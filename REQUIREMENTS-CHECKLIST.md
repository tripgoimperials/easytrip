# EasyTrip Semester Assignment Requirements Checklist

## 1. Working system
EasyTrip is a working online transportation booking and simulated payment system. A passenger can register, log in, search routes by date, view buses, select available seats, create a booking, choose a simulated payment method, receive confirmation, view an e-ticket, see booking history, and update a profile. An administrator can view system statistics and manage passenger accounts.

## 2. Required technologies
- HTML: page structure generated by PHP templates/pages.
- CSS: `style.css`.
- JavaScript: client-side interactions and Fetch/AJAX seat refresh.
- PHP: server-side application, authentication, OOP domain logic and API.
- MySQL: users, routes, buses, seats, trips, bookings, booking seats, payments and tickets.

## 3. Fetch/AJAX major operation
`seats.php` calls `api/seats.php?trip=...` with JavaScript `fetch()` every 4 seconds. The endpoint returns JSON containing currently unavailable seat IDs. The browser updates the seat map without reloading the page. The server still validates the selected seats during booking.

## 4. PHP OOP
`includes/init.php` contains these domain classes:
- `Database` - PDO connection.
- `Passenger` - registration, login and passenger retrieval.
- `Route` - route retrieval.
- `Bus` - trip search and trip details.
- `Seat` - seat availability.
- `Booking` - booking creation, expiration, retrieval and double-booking protection.
- `Payment` - simulated Card, USSD and Bank Transfer payment processing, including failed simulations.

## 5. MySQL storage/retrieval
Registration saves users to `users`. Search reads routes/trips/buses. Bookings save to `bookings` and `booking_seats`. Simulated payments save to `payments`. Confirmed bookings create records in `tickets`. Dashboard/history/ticket/admin pages retrieve records from MySQL.

## 6. API endpoint
`GET api/seats.php?trip={trip_id}` returns JSON. Successful response example:

```json
{"success":true,"trip_id":1,"taken":[4,7],"checked_at":"..."}
```

Invalid trip requests return HTTP 400 and JSON with `success:false`.

## 7. Simulated/test payment
The project does not perform real financial transactions. It supports Card, USSD and Bank Transfer simulations. Full card numbers and CVV are not stored. Card payment stores only the last four digits when successful.

## 8. Successful and failed operations to demonstrate
Successful examples: account registration/login, trip search, booking an available seat, successful simulated payment and ticket generation.

Failed examples: wrong login password, duplicate email/phone registration, invalid card details, explicit simulated failed Card/USSD/Transfer payment, and trying to book a seat another active booking already holds.

## 9. Double-booking protection
The system uses all of the following:
1. AJAX refresh to show recent seat availability.
2. Server-side validation before booking.
3. MySQL transaction and row locking (`FOR UPDATE`).
4. `UNIQUE (trip_id, seat_id)` on `booking_seats` as the final database safeguard.
5. Expired pending holds are removed from `booking_seats` before being marked expired so those seats become available again.

## 10. Database SQL submission
SQL scripts are inside the `database/` folder. For a new database, import `00_create_database.sql` through `09_tickets.sql` in numerical order. `10_admin_management_upgrade.sql` and `11_release_expired_seats.sql` are upgrade/maintenance scripts for an existing installation.
